## 一、项目概览

面向**单店主**的个人电商系统：店主管理商品/订单/统计，消费者浏览下单。核心链路（注册登录 → 浏览 → 购物车 → 下单 → 支付 → 发货 → 收货 → 后台管理/统计）是通的。

| 维度 | 内容 |
|---|---|
| 后端 | Spring Boot 3.1.5 / Java 17 / MyBatis-Plus 3.5.3 / MySQL 8 / BCrypt / 自研 JWT(HMAC-SHA256) / SpringDoc 2.5.0 |
| 前端 | Vue 3.4 + TypeScript 5.3 + Element Plus 2.5 + Pinia + Vite 5，17 个页面 |
| 代码量 | 后端 66 文件 / 2614 行；前端 43 文件 / 6222 行（其中视图 4951 行） |
| 部署 | Docker Compose（MySQL + Redis + backend + frontend），多阶段构建 + Nginx |
| 工程 | **非 git 仓库**，**零测试**（`backend/src/test/java` 为空目录） |

## 二、结构性优点

1. **分层干净**：`controller → service → mapper`，配 `entity / dto / vo` 分包，职责边界清楚，没有出现 Controller 直连 Mapper 的乱象（仅 `CartController`/`ProductController` 为省一次封装直接注入了 `SkuMapper`，可接受）。

2. **统一契约**：`Result<T>` 包装 + `ErrorCode` 枚举 + `GlobalExceptionHandler` 全局兜底，错误码分段（1xxx 用户 / 2xxx 商品 / 3xxx 订单 / 4xxx 优惠券）有规划。

3. **鉴权设计有想法**：`AuthInterceptor` 统一拦截 + `@RequiresAdmin` 注解式授权（`AuthInterceptor.java:73-79` 支持类级和方法级），比在每个 Controller 里手写 `if (role != 1)` 干净。`AuthUser` 通过 request attribute 传递，业务层不接触 `HttpServletRequest`。

4. **手写 JWT 的一个细节做对了**：签名比对用 `MessageDigest.isEqual`（`JwtTokenService.java:83`）而非 `Arrays.equals`，是常数时间比较，避免了时序侧信道。

5. **库存扣减是真正的亮点**（`OrderServiceImpl.java:112-131`）：

   ```java
   int productUpdated = productMapper.update(null, new LambdaUpdateWrapper<Product>()
           .eq(Product::getId, productId)
           .ge(Product::getStock, quantity)          // 条件写在 WHERE 里
           .setSql("stock = stock - " + quantity)    // 原子自减
           .setSql("sales = sales + " + quantity));
   if (productUpdated == 0) { throw ... PRODUCT_OUT_OF_STOCK; }
   ```

   这是**用 DB 行锁做乐观并发控制**的正确写法——不是「查库存 → 判断 → 再写回」那种典型超卖写法，而是把判断和更新合并成一条 SQL，靠影响行数判断成败。同一文件里的 `mergeOrderItems`（下单前按 商品+SKU 合并重复行，防止同一订单内重复计数）也是同类细节，说明作者对**数据准确性**是有意识的。这一块比多数同规模课程/练手项目的质量高一档。

6. **前端骨架完整**：`api/` 层按模块拆分、Pinia store 分域（user/cart/checkout/order/product）、路由 `meta.requiresAuth/requiresAdmin/guestOnly` 三级守卫、`AuthLayout`/`MainLayout`/`AdminLayout` 三套布局分离。

7. **部署配置有细节**：`docker/nginx/nginx.conf` 对 Vite 哈希资源做 `immutable` 长缓存、对 `index.html` 做 `no-store`、SPA fallback `try_files`；后端 Dockerfile 配了阿里云 Maven 镜像；compose 里用了 `healthcheck` + `depends_on: condition: service_healthy` 而不是裸 `depends_on`。

## 三、问题清单

### 🔴 阻断级：按 README 走会直接卡死

#### 1. 两份建库脚本分叉，README 指的那份是坏的

存在三份互相不一致的 SQL：

| 文件 | `deleted` 列 | 种子密码 hash | 状态 |
|---|---|---|---|
| `backend/src/main/resources/init/schema.sql` | ❌ 无 | 29 字符（无效） | README 让你用它，**坏的** |
| `docker/mysql/init/init.sql` | ✅ 有 | 60 字符（有效，密码 `123456`） | compose 实际挂载的，唯一正确 |
| `docker-entrypoint-initdb.d/init.sql` | ❌ 无 | 31 字符（无效） | 无任何配置引用，**死文件** |

**后果一**：`Product`/`User`/`Order` 三个实体都声明了 `@TableLogic private Integer deleted`，配合 `application.yml:17` 的全局 `logic-delete-field: deleted`，用第一份建库后调 `DELETE /api/product/{id}` 会执行 `UPDATE t_product SET deleted=1 WHERE id=?` → **Unknown column 'deleted'**。

**后果二更严重**：种子店主密码 `$2a$10$N9qo8uLOickgx2ZMRZoMye` 只有 **29 字符，bcrypt 要求 60 字符**。`BCryptPasswordEncoder.matches()` 对畸形 hash 一律返回 false，而管理后台所有页面都要求 `role=1`（`router/index.ts` 的 `requiresAdmin`）——**店主永远登不进去，后台完全不可用**。

#### 2. JWT 密钥硬编码且弱（`application.yml:24`）

```yaml
jwt:
  secret: mall2026secretkey   # 16 字符、无熵、明文进仓库
```

密钥是人可读的短字符串且随代码分发。任何拿到源码的人都能离线签发 `{"sub":1,"role":1}` 的合法 token，**直接获得店主权限**。这是本项目最严重的安全问题，必须改成环境变量注入的长随机串。

### 🟠 并发正确性：真实存在的竞态

#### 3. 订单状态流转不是原子的

`cancelOrder` / `payOrder` / `shipOrder` / `confirmOrder` 四个方法全是同一个模式（`OrderServiceImpl.java:145-208`）：

```java
Order order = getById(orderId);              // 读
if (order.getStatus() != 0) throw ...;       // 判
order.setStatus(4);
return updateById(order);                    // 写
```

读-判-写之间没有原子性。用户双击「取消订单」或重放请求，两个线程会都读到 `status=0`、都通过检查，各自执行一次 `restoreStock` → **库存被回滚两次**，凭空多出商品。支付/发货/收货同理会被重复执行。

有意思的是，同一个文件里的**库存扣减**已经用了正确的条件更新写法（`.ge(...)` + 检查影响行数），订单状态却没跟上——风格不统一，属于改一半漏一半。修法一致：

```java
int rows = orderMapper.update(null, new LambdaUpdateWrapper<Order>()
        .eq(Order::getId, orderId).eq(Order::getStatus, 0)
        .set(Order::getStatus, 4));
if (rows == 0) throw new BusinessException(ErrorCode.ORDER_CANNOT_CANCEL);
```

#### 4. `t_cart` 唯一索引在 NULL 下失效（`docker/mysql/init/init.sql:109`）

```sql
UNIQUE INDEX uk_user_product (user_id, product_id, sku_id)
```

MySQL 唯一索引允许多行同时为 NULL（`NULL != NULL`）。无规格商品 `sku_id IS NULL`，因此并发的两次加购会**都插入成功**，产生两条重复购物车记录；此后 `CartController.findCart` 用 `cartService.getOne(wrapper)` 单参数调用（默认 `throwEx=true`），多行结果会直接抛 `TooManyResultsException`。建议 `sku_id` 用 `0` 代替 NULL，或 `getOne(wrapper, false)` 后取首条。

### 🟡 安全（除密钥外）

- **Redis 是纯装饰**：`spring-boot-starter-data-redis` 在 pom 里、redis 服务在 compose 里、设计文档写「Redis（缓存/会话/验证码）」，但 **Java 代码中对 Redis 的引用数为 0**（已 grep 确认）。`/api/auth/logout` 是空实现 → **登出后 token 在 24h 内依然有效**，没有吊销机制。

- **公开接口白名单过宽**（`AuthInterceptor.java:57-69`）：`GET /api/product/list` 无需登录，且 `status` 参数不过滤 → 未登录即可拉到全部下架/草稿商品。`GET /api/product/{id}` 同样公开且 `ProductController.detail` 不校验 `status`，未登录可看下架商品详情。

- **Mass Assignment**：`CouponController.create(@RequestBody Coupon)`、`CategoryController.create/update(@RequestBody Category)` 直接绑定持久化实体，前端可越权写入 `receivedCount`、`status` 等本不该由客户端控制的字段。

- 登录接口无限流、无验证码（个人店铺可接受，但要知道）。

### 🟡 性能

- **`StatController.dashboard` 把 `t_order` 全表 `selectList(null)` 拉进内存**再做 stream 聚合（7 天趋势、状态分布、月销售额、客单价全在 Java 层算）。数据量小无感，但 `t_order` 上连 `create_time` 索引都没有（`docker/mysql/init/init.sql:74-93`），趋势查询全表扫描。这块完全应该下推成 aggregate SQL。

- `ProductManage.vue:312` 用 `getProductList({page:1, size:100})` 拉 100 条再在**前端过滤和分页**（`:255` 的 `matchesStatus`）→ 商品超过 100 个就**静默丢数据**。

- `ProductController.resolveCategoryIds` 递归查子分类，每层一次查询（N+1）。

### ⚪ 工程质量

- **零测试**：`backend/src/test/java` 是空目录，`package.json` 无 test 脚本、无 ESLint。库存扣减这种最该测的逻辑没有任何自动化验证。

- **非 git 仓库**，但源码树里堆着 `.idea/`（3 处）、`frontend/dist/`、`node_modules/`、以及一个 68KB 的 `admin-dashboard-fixed.png` 调试截图（全项目无任何引用）。`pom.xml` 末尾还留着 `<!-- force-rebuild-v2 -->` 这种调试注释。

- **死代码**：`frontend/src/utils/request.ts` 封装了 get/post/put/del，但**没有任何文件 import 它**（所有 api 模块直接用 `api/axios.ts`）。`SkuDTO.java`、`UserCouponMapper.java` 同样零引用。

- **`docker/scripts/deploy.sh` 会失败**：脚本里 `docker pull openjdk:17-jre-alpine`，而该镜像早已从 Docker Hub 下架，Dockerfile 用的也是 `eclipse-temurin:17-jre-alpine`——脚本和实际构建不一致。

- **全局异常一律返回 HTTP 200**（`GlobalExceptionHandler`），错误藏在 body 的 `code` 里，前端 axios 拦截器也配合这么判断。内部自洽，但破坏 HTTP 语义，网关/监控/APM 无法识别错误。

- `ProductController.update:90-97` 先 `updateById` 再单独补一条 `set(salePrice, null)`——因为 MyBatis-Plus 的 `updateById` 忽略 null 字段。能用，但绕路且两次写库。

## 四、总体评价

**这是一个骨架完整、分层清晰、主流程能跑通的电商练手项目，代码质量的"上限"和"下限"差距很大。**

- **上限体现在 `OrderServiceImpl`**：库存在 WHERE 里做条件扣减、下单前合并重复行、`GREATEST(sales-n, 0)` 防负销量——这些说明作者理解超卖是怎么发生的，不是照抄 CRUD 模板。
- **下限体现在周边全是壳**：SKU、优惠券、物流、退款、Redis 会话、XSS 防护，六项要么是空实现要么是纯 UI 摆设，而 README 和设计文档把它们都当成已完成功能写了出来。
- **最致命的单点是第 1 条**：README 指引的建库脚本本身缺列 + 密码 hash 无效。别人 clone 下来照着 README 走，第一步就卡在"密码正确但登不进去"，且报错信息毫无指向性。这是**交付可用性**问题，比任何代码风格问题都优先。
